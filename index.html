Profile

Hello — I'm AmirHossein

I'm a security researcher and software developer from Iran, and I work under the handle A-z-exe. My work sits where offensive security meets everyday engineering: I turn manual, repetitive testing steps into tools that other researchers can run, read and check.

I started with Python automation — small utilities that removed busywork. That habit grew into public tooling: a temporary-mailbox helper, the BugBountyToolkit for recon and checks, and dns-intel for DNS discovery and monitoring. Then I moved toward Android: auditing app permission sets, and building SchnellVPN, a Kotlin VPN client on Xray that speaks VLESS, VMess, Trojan and Shadowsocks.

Those threads came together in BBT OS, the project I spend most of my time on: an installable overlay for Kali Linux that puts recon, web, Active Directory, wireless, smart-card and access tooling behind a single launcher, so a bounty workflow starts from one desktop instead of a dozen terminals.

What I care about most is honesty in tooling. A tool should tell you what it checked, what it could not check, and how confident it is — and it should never dress up a guess as a finding.

Track record

How the tooling grew

  1. May 2025

    First public repository. bitcoin-key-educational-tool — a study of how keys, addresses and public-key derivation work, written to be read as much as run.

  2. Aug 2025

    From utilities to testing tools. temp-mail-generator, then BugBountyToolkit: Python reconnaissance and checks with scope-aware rules and report output.

  3. Feb 2026

    Into Android. AndroidPermissionChecker parses an app's manifest and scores its permission set from the outside, without installing anything.

  4. Jun 2026

    Intelligence and networking. dns-intel adds DNS records, certificate-transparency discovery and change monitoring. SchnellVPN brings that networking work to Android, in Kotlin.

  5. Nov 2026

    BBT OS and this site. A full Kali Linux overlay for bounty work — including a smart-card reader that can be reached over a VPCD relay — plus this page and its business card.

Approach

How I work

01Scope first

I only test assets that are explicitly in scope. Every tool I write is built to respect that boundary instead of quietly stepping over it.

02Verify, then report

A finding is a reproduction, not a scanner line. Anything I cannot confirm is labelled as unconfirmed or left out.

03Open by default

Source, setup steps and CI ship with the tool, so anyone can read the logic, run it locally and check my claims.
